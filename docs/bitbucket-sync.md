# Bitbucket Comment Synchronization

## Introduction

One of the most important parts of CodeGuardian is not only generating review suggestions, but publishing them in a controlled and maintainable way inside the pull request itself. In practice, this means the system must be able to create inline comments, identify which comments were generated by the agent, avoid touching comments written by developers, and update the pull request state incrementally instead of recreating everything on each execution.

This document explains how CodeGuardian synchronizes its review comments with Bitbucket and why the synchronization logic is an important part of the overall reliability of the system.

---

## Why Synchronization Is Needed

At first sight, posting comments to a pull request may look simple: the agent could just generate comments and publish them on every execution. However, that approach creates several problems:

- duplicated comments after repeated runs,
- stale comments that no longer match the current proposed fix,
- unnecessary noise in the pull request,
- and poor user experience for developers reading the review.

Because of that, CodeGuardian does not treat Bitbucket reporting as a simple "append-only" operation. Instead, it treats it as a synchronization problem: the agent computes the desired review state for the pull request, compares it with the current state, and only applies the necessary changes.

---

## General Strategy

The synchronization strategy is based on four steps:

1. Read the current pull request comments.
2. Keep only the comments that belong to CodeGuardian.
3. Compute the desired comments from the validated issues.
4. Compare both states and apply the minimum set of changes.

In other words, the goal is not to blindly publish new comments, but to make the pull request reflect the current validated output of the agent.

---

## Reading Comments from Bitbucket

CodeGuardian uses **Atlassian Rovo MCP** to read pull request comments.

### `get_pull_request_comments()`

This function retrieves comments page by page from Bitbucket using the MCP tool `bitbucketPullRequest` with the `comments` action. It handles pagination explicitly, collecting up to 100 comments per page until there are no more results.

This means the agent can read the full comment state of the pull request before deciding what to do.

### Why MCP is used for reading

The current architecture uses Atlassian Rovo MCP as the read layer because it provides a convenient way to retrieve pull request comment data through the existing tool interface. This fits well with the rest of the agent, which already uses MCP-based integrations for external systems.

---

## Identifying Agent Comments

A key requirement of synchronization is distinguishing agent-generated comments from human comments.

### Marker-based identification

CodeGuardian uses a hidden marker:

- `CODEGUARDIAN_AGENT_MARKER = "<!-- CodeGuardian-Agent -->"`

Every comment published by the agent is wrapped with this marker through `wrap_agent_comment()`. Later, when comments are read again, `is_agent_comment()` checks for the presence of that marker.

This mechanism is simple but effective:
- it does not depend on usernames,
- it does not require external storage,
- and it prevents the agent from modifying comments written by developers.

### Hidden issue identifiers

In addition to the global marker, each generated comment also stores hidden issue identifiers inside an HTML comment block. This block is produced by `hidden_ids()` and later read by `extract_issue_key()`.

This gives each comment an internal machine-readable identity that is later used during synchronization.

SonarQube comments keep their SonarQube issue keys. Optional performance comments use generated `PERFORMANCE:` keys based on the review type, file, scope range and scope content hash. This makes them distinguishable from SonarQube-backed comments while still allowing the existing synchronization logic to reuse unchanged comments and delete obsolete ones.

---

## Legacy Summary Comment Cleanup

### `get_agent_summary_comment_ids()`

The current implementation still includes logic to detect legacy summary comments created by the agent. It does this by checking both:
- the agent marker,
- and the summary title `CODEGUARDIAN_SUMMARY_TITLE`.

### `delete_agent_summary_comments()`

Before synchronizing inline comments, the agent removes those summary comments if they still exist. This is mainly a cleanup mechanism for previous iterations of the system and helps keep the pull request free from outdated top-level summaries.

Even though the current workflow is focused on inline comments, keeping this cleanup step is useful for backwards compatibility and repository hygiene.

---

## Reading Existing Inline Comments

### `get_inline_comments()`

Once all pull request comments are available, the agent filters them to keep only active inline comments generated by CodeGuardian.

For each valid comment, the function stores:

- the extracted issue keys,
- the file path,
- the target line,
- and a content hash based on the raw comment text.

This information is enough to compare the current comment state with the desired one later in the synchronization step.

### Why a content hash is stored

A file path and a line number are not enough to know whether two comments are really equivalent. The content hash makes the comparison more precise: if the proposed code or explanation changes, the hash changes too, so the agent can detect that the existing comment is no longer identical.

This is an important improvement over simpler synchronization strategies based only on file and line.

---

## Why Bitbucket REST Is Used for Writing

The current architecture uses **Bitbucket REST API** for creating and deleting inline comments.

### Reason for this split

The design intentionally separates reading and writing:
- reading is done through Atlassian Rovo MCP,
- writing is done through Bitbucket REST.

This mixed approach was chosen because inline comment creation and deletion are handled more reliably through the REST API in the current use case. In practice, this gives the system better control over the exact comment payload and the deletion process.

---

## REST Helpers

Several helper functions support the writing side of the synchronization process.

### `get_bitbucket_basic_auth_headers()`

Builds the authentication headers from environment variables. It supports the standard Bitbucket email/username plus API token combination.

### `ensure_bitbucket_rest_auth()`

Validates that the required REST credentials exist before trying to publish or delete comments. If the credentials are missing, it raises an `AgentExecutionError`.

### `get_bitbucket_api_base_url()` and `build_pullrequest_comment_url()`

These functions centralize the construction of Bitbucket REST endpoints. This makes the code easier to maintain and avoids duplicating URL patterns in multiple places.

### `create_inline_comment_by_rest()`

This function sends a POST request to create a new inline comment. It builds the JSON payload containing:
- raw markdown content,
- file path,
- and target line.

If the request succeeds, the function returns `True`. If it fails, it logs the status code or the exception and returns `False`.

### `delete_inline_comment_by_rest()`

This function sends a DELETE request to remove an existing comment. Like the creation function, it returns a boolean result and logs failures with enough context for troubleshooting.

### `delete_comment_ids()`

This helper deletes multiple comment IDs one by one and tracks which deletions succeeded and which ones failed. A short sleep is inserted between operations to avoid hitting the API too aggressively.

## Building the Desired Inline Comments

The synchronization logic does not work directly with raw issues one by one. It first builds the list of comments that should exist in the pull request.

### Input filtering

Inside `synchronize_inline_comments()`, the agent first keeps only valid issues that still have:
- a file,
- a solution,
- and a problem.

This avoids trying to build comments from incomplete issue objects.

### Grouping before publication

The valid issues are sorted by file and line range, then grouped and merged based on:
- matching signatures from `group_key()` (file path, original code, proposed code),
- proximity within a configurable merge gap (`CODEGUARDIAN_GROUP_LINE_GAP`, default 8 lines).

Issues that share the same signature and fall within the merge gap are merged into a single comment, reducing fragmentation and keeping the review cleaner.

### Building the comment content

For each issue group, the agent calls `comment_content()` to generate the final markdown body. This body includes:
- the file,
- the line range,
- the detected problem,
- the proposed solution,
- the original code block,
- the proposed code block,
- and the hidden issue identifiers.

---

## Synchronization Signature

One of the most important parts of the synchronization mechanism is the signature used to decide whether an existing comment is equivalent to a desired one.

### Desired signature

For each desired issue group, the current implementation builds a signature containing:

- file path,
- target line,
- ordered issue keys,
- content hash.

This is more robust than relying only on the line number or file path.

### Existing signature

For each existing CodeGuardian inline comment, the agent reconstructs the same kind of signature from the stored metadata:
- file path,
- target line,
- extracted issue keys,
- content hash.

### Why this matters

This design allows the system to detect several different situations:

- the comment already exists exactly as desired,
- the comment refers to the same place but has changed content,
- the comment is obsolete,
- or the comment is duplicated.

The content hash is especially valuable here, because it allows the system to detect real content changes instead of assuming that same file plus same line means same comment.

## The Synchronization Process

The main synchronization logic is implemented in `synchronize_inline_comments()`.

### Step 1: Read the current state

The agent retrieves all current active inline comments created by CodeGuardian.

### Step 2: Build the desired state

The agent generates the list of desired comment signatures and their associated issue groups.

### Step 3: Build the existing index

The agent converts existing comments into a dictionary indexed by signature. If duplicated existing signatures are found, the extra ones are marked for deletion.

### Step 4: Detect obsolete comments

If an existing signature is not present in the desired state, that comment is considered obsolete and added to the deletion set.

### Step 5: Delete obsolete comments

All comments marked for deletion are removed through `delete_comment_ids()`.

### Step 6: Create missing comments

For each desired comment that does not already exist, the agent publishes a new inline comment using `post_issue_group_comment()`.

### Step 7: Log the result

At the end, the function logs a synchronization summary with:
- desired comments,
- created comments,
- reused comments,
- deleted comments.

This makes the synchronization behaviour observable and easier to evaluate experimentally.

---

## Posting a Comment

### `post_issue_group_comment()`

This function is responsible for turning an issue group into a published inline comment.

It:
- selects the widest issue in the group as the base issue,
- checks that the target file still exists,
- computes the final target line,
- builds the markdown body,
- and sends the comment through the REST API.

If the comment is created successfully, the function logs whether it was a single-issue or multi-issue publication.

---

## Reporting Entry Point

### `report_to_bitbucket()`

This function is the public reporting entry point of the agent.

It performs three main tasks:

1. validates that a pull request ID exists,
2. checks that REST credentials are available,
3. opens an Atlassian Rovo MCP session and performs:
   - legacy summary cleanup,
   - inline comment synchronization.

From the point of view of the overall architecture, this function is the final bridge between the internal analysis results and the actual pull request state visible to developers.

---

## Reliability Benefits

The synchronization approach used in CodeGuardian provides several practical benefits.

### 1. It avoids duplicated comments

Because the agent compares the desired signatures with the existing ones, it does not create the same comment repeatedly on each execution.

### 2. It removes stale comments

If an issue no longer survives validation or if the comment content changes, the old comment is removed.

### 3. It preserves developer comments

Only comments marked as agent comments are touched. Human comments remain untouched.

### 4. It reduces pull request noise

Instead of clearing and rebuilding the entire review state every time, the system only applies the necessary changes.

### 5. It improves traceability

The synchronization summary logs make it possible to understand exactly what happened during each execution.

---

## Limitations

Even though the current synchronization logic is already quite robust, it still has some limitations:

- it depends on the agent marker and hidden IDs being preserved in the comment content,
- it assumes the file path and line metadata returned by Bitbucket remain stable enough for comparison,
- and it still works at comment level rather than at a deeper semantic level.

These limitations are acceptable for the current project stage, especially because the overall goal is to maintain a reliable and practical CI/CD review workflow rather than to build a fully stateful review platform.

---

## Possible Future Improvements

There are several directions in which this synchronization mechanism could evolve:

- richer metadata embedded in comments,
- versioned internal identifiers,
- support for threaded update strategies instead of delete-and-recreate,
- structured persistence of synchronization state outside Bitbucket,
- or more advanced conflict handling when code shifts between executions.

However, the current solution already solves the main practical problem: keeping the inline review comments aligned with the latest validated output of the agent.

---

## Conclusion

Bitbucket synchronization is one of the key reliability features of CodeGuardian. It transforms the reporting stage from a simple comment publication step into a controlled state reconciliation process.

This is important because the usefulness of an automated reviewer does not depend only on the quality of its suggestions, but also on how cleanly those suggestions are integrated into the pull request workflow. By identifying its own comments, rebuilding the desired state, and applying only the minimum necessary changes, CodeGuardian provides a more stable and less noisy review experience for developers.
