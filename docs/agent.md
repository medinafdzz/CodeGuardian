# CodeGuardian Agent

## Introduction

The `agent.py` file is the core component of CodeGuardian. It is responsible for connecting all the external systems involved in the pull request review workflow and for applying the logic that makes the process reliable.

At a high level, the agent receives the repository and pull request context, retrieves the relevant SonarQube findings, enriches those findings with source code context, groups them by scope, sends them to the language model, validates the generated fixes, and finally synchronizes the resulting inline comments back to Bitbucket.

This means that the agent is not just a wrapper around an LLM. It acts as the orchestration layer of the whole review process.

---

## General Responsibilities

The main responsibilities of the agent are:

- loading pull request metadata from the JSON file generated by the pipeline,
- retrieving SonarQube findings,
- detecting the affected scope of each issue,
- grouping findings before sending them to the LLM,
- requesting fix proposals from Gemini,
- optionally detecting static improvement candidates in changed files,
- optionally requesting non-blocking improvement suggestions from Gemini,
- validating the generated patches before publishing them,
- synchronizing inline comments in Bitbucket,
- and exporting execution metrics.

The file is organised in blocks that reflect these responsibilities.

---

## Core Data Models

The agent defines several small models that structure the data flow.

### `Issue`

The `Issue` model represents a single fix proposal generated by the language model. It includes the SonarQube key, file path, target type, target name, line numbers, problem description, solution description, original code, proposed code and required imports. This model is used as the main internal representation of a generated code suggestion.

### `Decision`

The `Decision` model represents the final output of the agent before reporting results back to Bitbucket. In the current version it contains:
- `issues`

This means the final result of the agent is essentially a list of generated issues or improvement suggestions that still need to pass normalization and patch validation before publication.

### `ScopeInfo`

`ScopeInfo` is a small immutable dataclass used to describe the scope around a finding. It stores:
- kind
- name
- start line
- end line

This allows the agent to reason about functions, methods or global code regions instead of isolated lines only.

### `IssueBatchDecision`

This model represents the JSON structure expected from Gemini for one batch of findings. It contains a list of `Issue` objects. It is used to validate the model response before the agent processes it further.

### `ImprovementCandidate`

`ImprovementCandidate` represents a static maintainability signal found before the optional improvement review calls Gemini. It stores the file, line, language, category, reason, evidence, original code and confidence score. The current implementation uses it for Python and shell/KSH improvement candidates.

### `AgentExecutionError`

This custom exception is used to signal controlled execution failures, such as missing credentials or failed external integrations. It makes the error handling more explicit and keeps the main flow easier to follow.

## Constants and Review Rules

The file also defines several constants that are important for the behaviour of the agent.

### Agent markers

Two constants are used to identify comments generated by CodeGuardian:

- `CODEGUARDIAN_SUMMARY_TITLE`
- `CODEGUARDIAN_AGENT_MARKER`

The marker is especially important because it allows the agent to distinguish its own comments from human comments in the pull request.

### Review rules for Gemini

The `REVIEW_RULES` string contains the core prompt instructions used to guide Gemini. It forces the model to:
- keep the original SonarQube key,
- return only valid JSON,
- propose real code modifications only,
- avoid unsafe refactors,
- preserve concrete types when needed,
- and return no issue if a safe fix cannot be produced.

These rules are one of the main control mechanisms in the system. They do not guarantee perfect output, but they significantly reduce the chance of unsafe or low-quality suggestions.

### Cache configuration

The file also defines several cache-related constants:
- `CACHE_METADATA_PATH`
- `CACHE_MODEL`
- `CACHE_MODE`
- `CACHE_TTL`
- `BATCH_CACHE_PATH`
- `BATCH_CACHE_MAX_AGE_SECONDS`

These values control how prompt caching and batch result caching are managed across executions.

## Cache Management

The cache section contains helper functions used to reuse prompt-related metadata and previous batch responses.

### `rules_hash()`

This function computes a SHA-256 hash from the review rules. It is used to detect when the rules have changed and therefore when cached prompt metadata should no longer be reused.

### `load_cache_metadata()` and `save_cache_metadata()`

These functions read and write prompt cache metadata from disk. The metadata is stored as JSON in a path defined by the environment. This makes prompt reuse persistent across executions.

### `cache_meta_valid()`

This function checks whether the stored prompt cache metadata is still valid. It verifies:
- model name,
- TTL,
- rules hash,
- and expiration time.

If any of those checks fail, the cache is considered invalid.

### `load_batch_cache()` and `save_batch_cache()`

These functions manage a second cache used for Gemini batch responses. The batch cache stores model responses on disk and reuses them when the same batch signature appears again.

The current implementation also invalidates the cache file if it is older than the configured maximum age.

## Atlassian Rovo MCP Integration

The agent uses Atlassian Rovo MCP to read pull request comments.

### `get_atlassian_mcp_url()`

Returns the MCP URL from the environment if present, or a default value otherwise.

### `get_atlassian_mcp_auth()`

Builds the authentication object for the MCP connection. It supports:
- Basic authentication
- Bearer authentication

If the expected header is missing or malformed, the function raises an `AgentExecutionError`.

### `atlassian_rovo_session()`

This async context manager creates and initializes the MCP client session. It wraps the authentication logic and provides a ready-to-use session object for reading pull request comments.

## File and Text Utilities

These functions support many parts of the workflow.

### `read_file_lines()`

Reads the contents of a file and returns the lines as a list. It is cached with `lru_cache`, which improves performance when the same file is accessed multiple times during one execution.

### `clean_replacement_text()`

Normalizes replacement text returned by the model. It converts escaped newline sequences into real newlines and removes markdown backticks. This is necessary because LLM output may include formatting artefacts.

### `normalize_code_block()`

Normalizes a block of code by trimming trailing whitespace line by line and unifying line endings. This makes code block comparisons more robust and reduces false mismatches due to formatting differences.

---

## Language and Scope Detection

This section is responsible for turning a raw SonarQube issue into a more structured input for the language model.

### `detect_language()`

Determines the programming language from the file extension. The current implementation supports Python, Java, JavaScript, TypeScript, Go, C#, C/C++, PHP, Ruby, Rust, Kotlin and Swift. Unknown extensions fall back to `"unknown"`.

### `resolve_scope_with_parser()`

This is one of the most important helper functions in the file. Its job is to infer the function, method or global scope that contains a given line number.

For Python, the implementation is indentation-based and searches backwards for a matching function definition.  
For brace-based languages, it uses a heuristic approach: it searches backwards for a likely function or method signature, then tracks brace depth until it finds the closing boundary of the scope.

This is not a full parser, but it is good enough for the current purpose of grouping findings at scope level.

### `resolve_scope()`

This is the safe public wrapper around the parser logic. It first detects the language, then calls `resolve_scope_with_parser()`, and if anything fails it falls back to a global one-line scope. This makes the scope resolution logic robust even when the file format is unexpected.

## Issue Normalization and Grouping

Before any issue is published, it is normalized and checked.

### `issue_key()`

Builds a stable identifier for an issue. If a valid SonarQube key exists, that key is used. Otherwise, the key is derived from file, line, target name and severity. This allows the agent to track issues consistently even when Sonar metadata is incomplete.

### `normalize_issues()`

This function cleans and filters the issues returned by the model. It performs several tasks:
- trims and normalizes text fields,
- converts severity to uppercase,
- normalizes the original and proposed code blocks,
- drops empty or identical replacements,
- fixes invalid line values,
- and deduplicates issues by SonarQube key.

This step is important because model output may still contain redundant or malformed results even when the prompt is strict.

### `group_key()`

Builds a grouping signature based on:
- file path,
- normalized original code,
- normalized proposed code.

This key is later used during inline comment synchronization to decide when issues should be grouped together as a single comment.

---

## Patch Validation

One of the most important reliability improvements in the current version of CodeGuardian is patch validation before publication.

### `patched_file_content()`

This function tries to reconstruct what the file would look like if the proposed patch were applied. It:
- reads the real file from disk,
- checks the original line range,
- extracts the original code slice,
- normalizes both the real code and the model-provided `original_code`,
- and only if they match, builds the patched file content in memory.

If the real code does not match the proposal, the function returns `None`.

### `validate_issue()`

This function applies validation to a single issue.  
First, it checks whether the proposed replacement matches the current file content using `patched_file_content()`.  
Then, if the file is Python, it also parses the patched content with `ast.parse()` to catch basic syntax errors.

This does not prove that a fix is semantically correct, but it prevents many invalid suggestions from being published.

### `filter_valid_issues()`

This function applies `validate_issue()` to a full list of generated issues and removes the ones that do not pass validation. It also logs the reason for each discarded issue.

---

## Comment Formatting

This group of functions is responsible for building the final comments published in Bitbucket.

### `extract_issue_key()`

Reads the hidden identifiers embedded inside a CodeGuardian comment and extracts the issue keys from them. This is used later to compare existing comments with the desired state.

### `hidden_ids()`

Creates a hidden HTML comment that stores issue identifiers in the generated comment body. This mechanism is important because Bitbucket comments need a machine-readable marker if they are to be updated or removed later.

### `wrap_agent_comment()`

Prepends the global agent marker to the comment body so the system can recognize that comment as machine-generated.

### `is_agent_comment()`

Checks whether a comment contains the CodeGuardian marker. This allows the agent to ignore comments written by developers.

### `comment_content()`

Builds the final markdown body of the inline comment. It supports both single-issue and grouped-issue comments. It also:
- includes file and line range,
- shows the detected problem and suggested solution,
- embeds the original and proposed code blocks,
- includes additional imports if required,
- and appends hidden issue identifiers.

This function is important because it converts the internal `Issue` objects into a human-readable review comment.

---

## Webhook and Repository Context

### `load_webhook_data()`

Reads the JSON file created by the pipeline and extracts:
- project key,
- pull request ID,
- repository slug,
- workspace.

If any required field is missing, the function logs an error and returns empty values.

### `get_code_context()`

Builds a small code snippet around a target line. This snippet is attached to each finding before sending it to Gemini, so the model can see the local code context of the issue.

---

## SonarQube Integration

### `clean_sonar_results()`

Parses the raw MCP tool response from SonarQube and converts it into a simplified list of dictionaries containing the most relevant fields:
- Sonar key,
- severity,
- message,
- line,
- file.

This reduces prompt size and keeps only the information the agent actually needs.

### `fetch_sonar_issues()`

This async function is responsible for the full SonarQube retrieval stage. It:
- starts the SonarQube MCP server through Docker,
- connects through MCP,
- requests unresolved findings in the new code period,
- parses the results,
- filters findings by severity and file existence,
- sorts them,
- limits the total number of findings,
- enriches them with code context,
- and resolves scope for each issue.

This is the main entry point for the static analysis signal that drives the rest of the agent.

---

## Gemini Integration and Batching

### `ensure_prompt_cache()`

Handles explicit prompt caching for Gemini. It tries to reuse an existing prompt cache if it is still valid, and otherwise creates a new one. This reduces repeated prompt costs across executions.

### `build_scope_batches()`

Groups findings into batches before they are sent to the language model.  
If a finding belongs to a function or method scope, it is grouped with other findings in the same scope.  
If it is outside any function or method, it is treated as a global standalone issue.

This batching strategy is one of the main architectural differences compared to a simple line-by-line review approach.

### `batch_signature()`

Builds a stable signature for each batch. The signature includes:
- project key,
- model name,
- review rules hash,
- issue metadata,
- scope metadata,
- and a hash of the actual scope content.

This makes the batch cache more reliable, because the cache depends not only on issue metadata but also on the real code block being analysed.

### `analyze_code_with_gemini()`

This is one of the central functions in the agent. It:
- creates the Gemini client,
- loads the batch cache,
- builds batches,
- optionally enables explicit prompt caching,
- prepares the prompt for each batch,
- reuses cached responses when available,
- calls Gemini when needed,
- validates the returned JSON format,
- collects the resulting issues,
- exports metrics to Prometheus Pushgateway,
- saves the updated batch cache,
- and returns the final `Decision`.

This function is the bridge between static analysis findings and model-generated fix proposals.

## Optional Improvement Review

The improvement review is a separate path from SonarQube-backed defect fixing. When enabled, it:

- reads the changed files from the pull request diff,
- applies default and configurable exclusions,
- detects static improvement candidates in supported files,
- sends those candidates and bounded diff context to Gemini,
- receives non-blocking `IMPROVEMENT` suggestions,
- and reuses the same normalization, patch validation and Bitbucket synchronization pipeline as normal issues.

The current detectors are intentionally small and explainable:

- Python long functions,
- Python broad exception handlers,
- shell loops based on command substitution,
- unquoted shell variables in test expressions.

This design keeps the LLM as a proposal engine rather than the only source of improvement detection. The current limitation is that the model response is not yet strictly linked back to a candidate identifier; this is a natural next step for future work.

## Pull Request Comment Reading

### `get_pull_request_comments()`

Uses Atlassian Rovo MCP to retrieve pull request comments from Bitbucket, handling pagination when necessary.

### `get_agent_summary_comment_ids()`

Finds legacy summary comments created by the agent. This is useful to remove outdated summary comments and avoid noise in the pull request.

### `get_inline_comments()`

Reads existing inline comments from the pull request and keeps only the ones created by CodeGuardian. For each one, it stores:
- extracted issue keys,
- file path,
- target line,
- content hash.

This information is later used to decide whether an existing comment can be reused or should be removed.

---

## Bitbucket REST Helpers

The agent uses the Bitbucket REST API for inline comment creation and deletion.

### `get_bitbucket_basic_auth_headers()`

Builds the HTTP authentication headers from environment variables.

### `ensure_bitbucket_rest_auth()`

Checks that the required REST credentials are present before trying to publish comments.

### `get_bitbucket_api_base_url()`

Returns the Bitbucket API base URL, either from the environment or from the default public API endpoint.

### `build_pullrequest_comment_url()`

Builds the REST URL for a specific pull request comment.

### `create_inline_comment_by_rest()`

Creates a new inline comment in Bitbucket by sending a POST request. It returns a boolean result and logs any HTTP or unexpected errors.

### `delete_inline_comment_by_rest()`

Deletes an inline comment through the Bitbucket REST API. Like the creation function, it returns a boolean and logs errors.

### `delete_comment_ids()`

Deletes a set of comment IDs one by one and keeps track of successful and failed deletions. This function is mainly used during synchronization to remove obsolete comments.

---

## Synchronization and Reporting

### `post_issue_group_comment()`

Publishes a validated issue group as one inline comment. It determines the most representative issue in the group, computes the target line, builds the final comment content and sends it through the REST helper.

### `delete_agent_summary_comments()`

Removes legacy summary comments that were previously created by the agent. This keeps the pull request cleaner and avoids duplicated summaries.

### `synchronize_inline_comments()`

This is one of the most important functions in the reporting layer. It:
- reads current inline comments,
- filters valid issues,
- groups issues that should appear together,
- builds the desired comment signatures,
- compares them against the existing signatures,
- deletes obsolete comments,
- reuses matching comments,
- and creates only the missing ones.

The current signature includes file path, target line, issue keys and a content hash, which makes synchronization precise and prevents stale comments from surviving when the actual content has changed.

### `report_to_bitbucket()`

This function is the final reporting step. It:
- validates the pull request ID,
- checks REST credentials,
- opens an Atlassian Rovo MCP session,
- removes old summary comments,
- synchronizes inline comments,
- and logs the result.

This is the final step that makes the agent visible to developers inside the pull request review itself.

---

## Main Execution Flow

### `main()`

The `main()` function coordinates the full agent execution. It:
- reads the input JSON,
- retrieves SonarQube issues,
- exits early if no relevant issues are found,
- runs Gemini analysis,
- normalizes and validates the generated issues,
- determines whether blocking findings exist,
- logs an execution summary,
- and reports the final issues to Bitbucket.

The logic is intentionally linear and explicit, which makes the execution flow easier to understand and debug.

---

## Error Handling

The script ends with a standard async entry point wrapped in controlled exception handling.  
`AgentExecutionError` is used for expected operational failures, while any unexpected exception is still logged with a full traceback before the process exits with a non-zero code.

This is important because the agent is designed to run inside Jenkins, where clear logs and exit codes are necessary for troubleshooting.

---

## Final Remarks

The current version of `agent.py` reflects the evolution of CodeGuardian from a simple proof of concept into a more controlled and reliable review component.

Its most important qualities are:
- clear separation of stages,
- scope-aware batching,
- validation before publication,
- incremental synchronization of comments,
- and execution metrics for monitoring.

Even though some future improvements are still possible, the agent already provides a strong functional base for automated pull request review in a CI/CD environment.
